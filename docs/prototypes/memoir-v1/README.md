# 回忆录成书层原型 v1

把老人确认过的回忆重写成一本抒情、按六模块分章的回忆录（原型 + 评测）。用户决定（2026-10-24 ～ 10-26）见任务书；本目录记录交接规格、流程、量表、迭代结果和接入后端的方案。

- 交接规格：[handoff.md](handoff.md) + [handoff.schema.json](handoff.schema.json)
- 题目分类：[question-depth.json](question-depth.json)（23 故事 / 23 事实 / 37 感悟）
- 迭代记录：[ITERATIONS.md](ITERATIONS.md)
- 代码：`tools/memoir_eval/`（inputs.py 输入构造、book.py 规划→写作→核对→组装、render.py 导出、score.py 量表、book_queue.py Haiku 队列、prompts/ 全部提示）

## 1. 两层：事实和文采分开

1. **如实草稿层（现有，不改）**：每题答完，GROUNDED_DRAFT_PROMPT 只整理不添加，老人确认事实后保存为一段回忆。
2. **成书层（新增）**：制作回忆录时，把这些确认过的回忆按章重写。每一句都标出依据的原话编号；写作者加的句子（替老人说的感受、回望、过渡、意象、呼应、收束）一律标出类型，整章预览时由老人/家人逐句确认。核对不过的段落退回如实草稿原文，不编。

## 2. 流程（tools/memoir_eval/book.py）

| 步骤 | 做什么 | 调用 |
|---|---|---|
| 输入 | 交接数据（handoff）：每题原话全文与问句、已确认草稿、字段状态、记不清/不愿讲、时间线索、称呼 | 0（app 数据由后端读表；测试素材见 handoff.md §5） |
| 并章（代码，规划之前） | 某模块原话不到 1500 字，就和相邻的一个模块并成一章（取较短的一边）；一章最多两个模块，六模块结构保持可见；邻居都已并过就保留为短章；序章不并 | 0 |
| 规划 | 每章放哪些故事、一节一个故事、并成一章的两个模块打通按时间排节；短的事实题并入相关的节；感悟题拆到相应章节章末；序章只交代“我是谁”；章名从原话里的物件或原话取（代码核对 title_quote 逐字出现在原话里）；贯穿全书的呼应线索；私事单列。漏排的单元由代码补回原模块那一章（同模块最后一节之后） | 1 次 / 本（deepseek-v4-pro，**思考模式**，`plan-v3.txt`） |
| 预算（代码） | 各章预算 = 本章原话字数 × 档位倍数（简本 0.5 / 标准 0.7 / 详本 1.0），且不超过 全书上限 × 章占比之和（序章 5%、童年 15%、求学 15%、工作 22%、家庭 17%、后来 11%、回望 13%；上限 简 2 万 / 标 5 万 / 详 9 万） | 0 |
| 写作 | 每章一次（预算超过 6000 字的章分段调用；`write-v3.txt`，关思考）；输出结构化 JSON：节 → 段 → 句，每句 `src` 原话编号、`add` 加写类型；代码再做一次繁转简 | 1 次 / 章 |
| 核对 | 代码：每句里的数字（阿拉伯数字与中文数字归一）、地名（省市县乡镇村…结尾）、人名（老X/小X/X老师…）必须出现在原话中；“几百年/上千/数十”这类模糊量级也必须在原话里出现；模型：每章一次（`check-v2.txt`，关思考，附本书其他章原话以免把跨章呼应当成编造），逐句找“原话里没有的事”（无来源事实、张冠李戴、确定化、写了不愿讲、未标加写、加写含事实） | 1 次 / 章 |
| 回退（代码） | 有问题的加写句删掉；未标的感受改标为加写（仍交老人确认）；其余有问题的事实句，整段退回如实草稿——按句匹配：取所引题目草稿里与这段每句最相近的句子，不把别处已写过的内容带回来；写作调用失败的章节整节退回草稿 | 0 |
| 组装 | Markdown + 审阅 HTML（加写句高亮并标类型，每段可展开看原话来源，退回段标“如实草稿”，章末列本章加写句，书末列没写进书的私事/不愿讲） | 0 |

## 3. 量表与指标（先固定，再迭代）

Haiku 盲评，每章一个请求（`prompts/rubric-v1.txt`，队列 memoir）：看这一章正文（加写句标出）和这一章用到的老人原话，不知道版本、轮次和人物分组。5 项 1–5 分：

- **忠实**：有无编造、张冠李戴、记不清写成确定、加写句带进新事实；并逐字列出编造之处（fabrication）。
- **细腻抒情**：是否靠老人讲过的细节打动人、加写是否克制贴切；空泛煽情、堆形容词、套话扣分。
- **连贯可读**：按时间、按故事展开，过渡自然，无重复跳跃。
- **口吻**：像不像老人本人（称呼、口头语、说话方式），书面腔/作家腔扣分。
- **结构与篇幅**：一节一个故事、章末收束；篇幅与原话素材相称，不注水、不丢重要的事。

代码指标（每本）：成书字数 / 原话字数、照搬率（非加写句中，与原话有一段连续相同文字覆盖该句 80% 以上的字数占比；衡量是“写”还是“誊”）、加写句占比、来源中找不到的数字/地名/人名数、原话单元利用率、各章字数与预算的平均偏差、退回如实草稿的段数；以及流程统计（模型核对发现数、删掉的加写句、改标的句子）。

代码指标里“来源中找不到的数字/地名/人名”在最终书中都是 0（找到的句子已被删掉或退回草稿）。

要点：

- **v1 其实是在誊写原话**（照搬率 0.9 左右，忠实近满分、抒情只有 3.1–3.3）。抒情的提升主要来自 v3 的虚构示例和“引语以外不连续照抄超过十个字”的硬规则（+0.39）；结构的提升来自先并章、跨模块按时间排节、按句退回（不再整段重复）。
- **照搬率没到 0.5**（最终 0.64–0.66）：关思考的模型仍保留大量原话短语。这些短语多是老人的说法，口吻分反而最高；再往下压就要更多“替老人说”，留出组已经看到加写里添小画面的编造。按“忠实优先”没有再加码。
- **忠实在留出组掉到 4.31**：6 处编造里 4 处是加写句或叙述里添的小画面（“一个人扛着锄头”“一张桌上”“一个锅里”），1 处把“可能是”写成确定。迭代组 4.77、留出组 4.31，说明 check-v2 放宽后对这类小画面拦得不够，上线前要收紧（见 §6 和“需要决定的问题”）。
- 已知问题：规划把单元移到别章后会留下很短的章（如 117 字预算）；写作会漏写素材（单元利用率 0.69–1.0，黄小荣“双职工”章丢了恋爱经过）；薄素材里同一件事在两章各写一遍；加写句句式偏单一（“现在想想……”）。

### 思考模式的取舍

| 步骤 | 选择 | 依据 |
|---|---|---|
| 规划（每本 1 次） | **开思考** | 只有这一步开；每本约 2 万 token（八成是思考），一轮约占 25–30%。负责分节、跨模块按时间排序、感悟题拆章，是结构分数的来源。 |
| 写作（每章 1 次） | 关思考 | 第 1 轮同一批 7 本开/关对比：五项分差都 ≤0.2、互有高低；开思考每次约 2.4 万 token（关 1.0 万）、耗时约 5 倍。 |
| 核对（每章 1 次） | 关思考 | 第 2 轮同一批 16 章开/关各核一次：开 3 处、关 2 处、重合 1 处，开思考多抓到 1 处“确定化”，token 约 2 倍。差距不大，先关；但留出组的编造说明核对是最该加强的一步，若要开第二个思考步骤，应开在这里。 |

## 6. 接入后端的方案（只写方案，本分支不改后端）

### 6.1 放在哪

- **新服务** `app/services/memoir_book_service.py`：读交接数据（handoff，见 handoff.md 的映射）→ 规划 → 按章写作 → 核对与回退 → 存成书版本。提示文件用原型最终版（`plan-v3.txt` / `write-v3.txt` / `check-v2.txt`），放 `app/ai/memoir_prompts/`，带版本号。代码核对（数字/地名/人名）直接搬 `tools/memoir_eval/mb.py` 的 `numbers / places / persons / unsupported`。
- **新表**
  - `memoir_books`：id、person_id、family_id、edition（brief/standard/full）、status（planning/writing/review/confirmed/stale）、source_revision（交接数据哈希，缺口 G6）、plan（JSON：章、节、并章、呼应线索、私事清单）、prompt_version、model、created_at、version（乐观锁）。一个人物可以有多个版本，设置里指向当前版本。
  - `memoir_book_chapters`：book_id、index、modules、title、status（queued/writing/ready/failed/confirmed/stale）、content（JSON：节 → 段 → 句，句带 src 与 add）、check_report、source_revision（本章用到的原话哈希）、confirmed_at、revision。
  - `memoir_book_decisions`：chapter_id、sentence_id、decision（keep/delete/edit/include_private）、text（改写后）、decided_by、decided_at。加写句的确认、私事是否写进书都记在这里。
  - 缺口 G1/G2 需要的 `memories.question_id/interview_module` 列与人物级题目台账（见 handoff.md §4）。

### 6.2 何时触发

- 用户在回忆录设置里选“按章节成书”并点“生成”时：先一次规划，再按章排队写作（每章一个后台任务，单 worker 下按人物串行；规划开思考模式，约 3–5 分钟、约 2 万 token；写作、核对关思考，单章约 30–60 秒，原型里原话约 0.4–1.2 万字的书全流程约 5–12 万 token（规划约占三成）；素材达到标准本（原话 6 万字上下、10 章以上）时，核对附全书原话会占大头（每章都带一遍），上线时改为只附加写呼应句所引的单元；必须异步，App 轮询章状态，写好一章显示一章）。
- 每章可单独“重写这一章”；新的回忆保存后，用到的题目变了的章标为 stale，提示“有新回忆，可重写这一章”，不自动覆盖已确认的章。
- 写作或核对失败：该章退回如实草稿拼成的版本（不编），状态 ready 并标“按如实草稿排”，可稍后重试。

### 6.3 老人确认加写句的交互

- 整章预览：正文里加写句用浅底色标出（与原型 HTML 相同），点一下弹出“这句是帮您加的（感受/回望/意象…）：保留 / 删掉 / 改一改”；事实句点开可看“您当时是这么说的”原话。
- 章末“没写进书的内容”：私事、不想讲的，逐条“写进去 / 不写”；选“写进去”后重写本章。
- 整章确认后才进 PDF；未确认的章在 PDF 里按如实草稿排，或整章不出（设置里选）。

### 6.4 与现有回忆录设置 / PDF 的关系

- `MemoirSettings` 加 `layout: 'stories' | 'chapters'`（“按篇排列”/“按章节成书”，默认按篇，现状不变）和 `edition`；`MemoirSnapshot` 在 chapters 模式下多返回当前成书版本的已确认章节（章名、模块小标题、节名、段落文字），stories 字段照旧。
- 客户端 PDF（iOS `MemoirPDFRenderer.render`、Android `MemoirPdf.render`）现在“一篇回忆 = 一章”：标题 + 日期地点 + 正文 + 照片，目录列每篇标题。chapters 模式下改为：目录列“序章/第一章 + 章名”，章首页“章名 + 模块名”，节名作小标题，正文按段排；照片放在引用了该回忆（段落 src → 题 → memory_id）的那一节之后，沿用现有的照片选择与排除设置。加写句在 PDF 里不再标色（已确认）。
- 现有的封面、书名、字号设置不变。

### 6.6 上线前要补的（来自留出组）

- 核对收紧：加写句里的具体画面（动作、器物、人数，如“扛着锄头”“一张桌上”）也算事实，必须在原话里出现；“可能/好像/大概”被去掉要报“确定化”。可在核对这一步开思考（每章约多 1 万 token），或加一道代码规则：加写句里出现的名词须在原话中出现。
- 写作漏写：写完后代码检查各节原话单元是否都被引用，漏掉的故事题单元单独补写一次（只写这一节），而不是退回草稿。
- 薄素材：规划先合并重复的事（同一件事答在两题里），素材不到约 1500 字时全书只写序章 + 一章。
- 加写句句式去重：同一章里“现在想想……”这类开头不超过两次（代码检查，超了让写作重写该句）。

## 7. 需要用户决定的问题

1. 忠实与文采的平衡点：留出组忠实 4.31 / 抒情 3.77。是接受“加写里有小画面、全部交老人逐句确认”，还是收紧到“加写只许感受和回望、不许任何画面”（预计抒情回落到 3.5 左右）？
2. 核对要不要开思考：开了每章多约 0.6–1 万 token（一本 3–5 章约多 2–5 万）、多抓“确定化”；不开靠代码规则补。
3. 标准本倍数：原型用 0.7 倍原话（测试素材原话 0.4–1.25 万字，成书约 0.35–1.15 万字），离“标准本 4–5 万字”很远——真实 App 素材量要先看采访那边一次完整访谈能出多少原话。
4. 并章：一章最多两个模块（主控意见）后，素材少的模块会成为几百字的短章；可以接受，还是短于约 500 字的章并入相邻章作为一节（带模块小标题）？
