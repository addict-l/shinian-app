# T05 部署与恢复方案

T05 维护的是一段已保存回忆及其来源故事片段。同一成员的其他故事和新的待整理讲述不在删除范围内。客户端手工修改标题正文不调用模型，不改变原始聊天；重新生成需要明确确认，失败仍保留原草稿。更新与删除都核对服务器版本，冲突时保留本机修改供比较。

## 兼容迁移

迁移 `d10100000001 → e10100000001` 增加可空的照片编辑归属字段、图片清理任务表和已删除回忆的重试凭据表。旧照片和旧回忆不改写。照片上传先暂存，保存编辑时才关联正式回忆。移除聊天原有照片只解除回忆展示关联，原始聊天继续保留；整段删除才清除其来源讲述、故事回复、草稿及全部照片；成员共同开场白先在同一事务中移入独立内部记录，保留消息标识、正文与时间，避免被来源片段级联删除。开场记录不参与待整理片段选择或下一篇事实提取，仍遵循最近 20 条展示规则。旧版首条助手欢迎消息兼容保留，用户之后的普通助手回复不会被误保留。本次开场白修正无需新增数据库迁移。

数据库关系在一个事务中删除，照片任务同事务落库，提交之后才清理文件。请求返回后以及服务启动后每 15 秒重试清理。文件已不存在视为完成，权限错误保留任务，下次再试。重复的整段删除请求根据家庭和版本读取删除凭据，不重复删除其他记录。

## 验证和部署顺序

1. 本机独立 MySQL 数据库运行迁移、后端测试；原 iPhone 17 Pro（`82915145-6254-4561-9028-8F8F8D636B89`）运行客户端状态及界面测试，独立副本构建 Release。
2. 将不含环境密钥、用户数据和测试产物的后端源码、测试源码上传到 `/opt/shinian-validation/releases/t05-20261011`，构建 `shinian-api:candidate-t05`。在一次性 MySQL 测试数据库执行迁移和测试，不修改正式家庭数据。
3. 正式部署前在 `/opt/shinian-validation/backups/pre-t05-20261011` 保存仅 root 可读的数据库、照片、后端源码、运行镜像和基准提交；正式业务计数和接口只读检查留档。
4. 同步已验证后端，启动同一个候选镜像完成迁移。检查健康、契约、原有会话与回忆读取、迁移版本、HTTPS 认证边界和业务表计数。前端源码另行上传并逐文件校验哈希；阿里云不编译 iOS。
5. 将最终独立 Release 安装到原模拟器供人工审查。只有用户认可后才执行云端、验证目录和主工程提交与推送。

## 恢复

部署失败先保留错误日志与当前数据，不自动回灌旧数据库。新增结构允许旧业务代码读取：紧急恢复旧镜像时应使用 Compose 临时 command 启动原镜像的 `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1`，绕过旧镜像不认识新版本的 Alembic 启动步骤，并保留新迁移结构，待修复后恢复正常启动。

需要真正回退结构时，先停止写入，在当前 T05 镜像中完成清理任务，并保存或丢弃暂存照片，再执行 `alembic downgrade d10100000001`。迁移在存在待清理文件或暂存照片时拒绝回退，防止丢失清理依据。随后切换旧源码与镜像、重启并只读校验。仅在明确接受恢复时点以后数据丢失且取得授权后，才使用部署前数据库与照片备份整体恢复；不能只恢复其中一项。

文件删除属于用户明确确认的不可撤销操作。部署备份用于故障恢复，保留在 root 目录，界面不得声称导出的外部 PDF 会被收回。

## 开场白修正部署补充（2026-10-11）

候选源码与验证目录独立放在 `/opt/shinian-validation/releases/t05-opening-20261011`，先在随机临时数据库验证，不修改正式业务数据。部署前将当前 T05 源码、数据库、媒体与运行镜像备份到新目录 `/opt/shinian-validation/backups/pre-t05-opening-20261011`，镜像保留为 `shinian-api:t05-before-opening-fix`。无需数据库迁移，仅替换已通过检查的镜像。部署后只读核对健康、契约、现有会话及六张业务表记录数。需要回退时恢复该备份源码并重启备份镜像；没有运行迁移，不需降级数据库。iOS 最新 Release 安装到原 iPhone 17 Pro 模拟器，提交继续等待用户审查。

## 开场白预生成修订部署（2026-10-11）

不新增数据库字段或迁移：创建人物时同步生成并校验开场白，将人物、状态为 prepared 的初始内部片段及 opening 消息同事务保存。prepared 不计为已发布聊天历史；第一次打开空聊天时，在人物锁及事务内发布同一消息。客户端从人物接口的 opening_message 与 has_chat_history 判断是否可提前显示，消息 ID 与后续历史一致。已有历史不追加欢迎；既有开场删除保护继续适用。模型失败时不创建半个人物，表单内容和请求标识供用户重试。旧人物空历史保持一次补生成兼容路径。

候选版本及验证放在 `/opt/shinian-validation/releases/t05-prepared-opening-20261011`。部署前备份当前源码、运行镜像、数据库和媒体到 `/opt/shinian-validation/backups/pre-t05-prepared-opening-20261011`，镜像标记 `shinian-api:t05-before-prepared-opening`。先在随机测试数据库检查，然后部署候选镜像，正式服务只读检查人物开场字段、状态、历史和业务计数。真实模型开场验证仅使用合成姓名及家庭身份，并禁止连接业务数据库。回退保留数据库结构，切换该备份镜像及源码；新消息类型和 prepared 状态仍可由上一版本读取。客户端继续在原 iPhone 17 Pro 验证和安装；T05 仍待人工审查后提交。

## 旧空会话客户端修正及最终归档（2026-10-11）

恢复 GET 保持只读。客户端读到空人物聊天时进入已有的幂等 POST 人物会话入口；空快照不能遮住人物接口提供的预生成欢迎。只修改客户端，不重新部署后端或运行迁移。使用当前镜像在独立测试库验证，前端归档核对留在 t05-empty-opening-20261011，独立 Release 安装原模拟器。正常 UI 完成旧空历史人物开场验证，用户人工审查通过并授权提交；此前待审查说明保留为历史。
