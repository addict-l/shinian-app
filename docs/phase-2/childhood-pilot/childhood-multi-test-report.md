# 童年采访：四组真实后端连贯性测试

2026-10-14。结论：**长回答的普通流程比较顺，但整体连贯性尚未通过，暂不能据此认定适合老人直接使用。** 短回答暴露了错误承接和提前收尾，明确跳过会中断，更正人物后完整性判断会变化。

本轮只测试现有实现，没有修改 Prompt、后端采访逻辑或发布正式环境，也没有 commit / push。此前 301 项回归和一组顺利访谈的结果仍属实，但只能证明对应样例与接口行为，不能覆盖本轮暴露的对话质量问题。

## 怎么测的

使用 4 位虚构人物，各准备 6 件不同童年回忆，通过阿里云隔离后端实际调用 `deepseek-flash`，从当前主问题开始，按真实返回的子问题作答，生成草稿、确认保存，再打开下一题。

人的回答来自固定底稿，不由另一个 AI 临场编造。短答组按当前目标每次只给一个小信息；没有被问到的后续素材没有偷偷补进去。底稿没有准备某个子问题的回答时，脚本使用“这一点我已经记不清了。”；这种兜底会影响对话和草稿，**不能当作真实老人会这样回答的证据**。实际发生处可在短答第 6 题、补充组第 2 题看到。

不包含突然转到另一件故事、开场与人生骨架、其他人生模块、真实老人操作、语音、客户端联调、整章写作或 PDF。这里检查的是童年模块中的采访与保存推进。统计中的“代码合格”只是当前覆盖率规则，不能代替人工判断故事内容。

## 连贯性问题的实际证据

### 1. 用户已经选定一件事，仍要求重新选

M02 第 1 题：

> 人：小时候我帮家里打水。
>
> AI：您想先讲其中哪一件事？

这里只有打水一件事，问“其中哪一件”不自然。相同问题还出现在 M02 找眼镜、M03 看母亲做粥。后端在 `activity` 未被抽成 present 时，直接套用选事件模板，未校对用户是否已经明确选定事件。

建议：区分“已选主题但缺经过”与“有多件事需要选择”。活动概述足以确定当前主题，再追问一个具体片段。

### 2. 没有提到别人，却问“这位是谁”

M02 第 1 题，用户讲自己到井边放桶、系绳子后：

> AI：您刚说的这位是谁？
>
> 人：那次是我自己去的。

此时没有一个“这位”可供指代。回答后 `context` 仍是 false，流程已经转入补充与保存。人物抽取和问题模板两个环节都没有正确接住“本人独自做”的情形。

建议：只有原文出现未明确身份的他人，才能追问这个称呼；明确本人独自参与即可完成参与者信息。

### 3. 子问题答完，不等于整件故事讲完

M02 第 2 题：

> 人：小时候姐姐帮我补衣服。
>
> AI：您记得那次接着发生了什么？
>
> 人：她拿针线来补。
>
> AI：这段可以先整理成草稿了。您还有什么想补充的吗？

后端此时 `answer_status=answered`，但 `coverage.process=false`。该子问题被加入已答目标后，没有新的可问目标，控制器把“没有下一条问题”转成了保存邀请。没有达到追问上限，也没有用户拒绝经过，仍然提前收尾。

允许用户随时保存现有素材是已确认的产品规则，应保留。缺陷在于自动收尾没有区分“故事已经充分”与“当前只够保存少量片段”。

建议：回答 AI 完成当前子目标后，事件 AI 根据累计素材选择**另一个尚缺的具体目标**；不要因为同一个目标已答而跳过整件事件的缺口，也不要重复原问题。

### 4. 两个动作和一条连接，不足以证明故事经过完整

M03 第 2 题：

> 人：小时候父亲给我做过木头小车，我看着他弄。具体制作过程记不清了。

后端把“做过木头小车”“看着他弄”各记为 actual，又把并列的制作与观看记成 sequence，最后 `coverage.process=true`。模型还报告了经过未知，但覆盖率计算没有据此区分“保留片段”与“完整故事”。

这里没有得到制作过程中发生的具体变化，也没有得到一次相处中本人回应的展开。可以尊重记不清并保存，但不宜用这个条目支撑“模块内容已经充分”。

M02 剥豆子的草稿只有“小时候我帮母亲剥豆子。豆子掉到盆外了。”，代码也给出全部覆盖。其状态内“剥豆子”和“帮母亲剥豆子”还重复保留为两个单元。这不只是文案问题，也涉及概述、具体经过及重复动作的判定。

建议：以题库规定的语义目标检查故事，而不是机械数动作。活动概述不能重复计数，两个并列动作不能自动算先后；达到保存条件与达到章节素材条件应分别标记。

### 5. 明确要求跳过会返回错误

M03 第 5 题：

> 人：童年时家里没什么我记得的变化，这一题我想先跳过。

首次请求 2.451 秒返回 502；使用同一 `client_request_id` 和原文重试，2.744 秒仍返回 502，接口提示原文已保留。

只读复查确认：这句话只保留了一次，当前仍停在第 5 题 opening，之前 4 件回忆仍已保存。

原请求日志记录 `GuidedEventAssessment` 校验失败。为定位原因，另用相同原文和背景进行一次**不写数据库的模型诊断**：模型两次把 activity 判为 declined，且逐字引用“我想先跳过”；后端两次均以 `Guided unavailable fact needs explicit user evidence` 拒绝。现有校验只接受“不想、不愿、不讲”等少数表达，没有包含“跳过”。

这次复现说明失败来自后端证据校验与用户意图表达不匹配，不能归因于网络慢。原始 HTTP 没有记录模型内部 JSON，诊断结果是单独复现，不冒充原请求逐字日志；诊断调用也不计入上述 155 次 HTTP。

建议：明确跳过应由控制器直接承接，记录未采集并推进题目，不创建空回忆、不等待模型改写成拒答关键词。

### 6. 更正称呼会改变对既有经过的判断

M04 第 2 题已经讲到递线、线缠起来、解开。第一次抽取把“线缠起来”标为 static，连接经过 static 单元后，现有代码无法识别完整链，于是继续问“接着发生了什么”。脚本没有准备这项多余追问，兜底回答记不清。

下一轮，同一句“线缠起来”被重新标为 actual，代码判经过完整；更正“纳鞋垫的是外婆，不是母亲”后，又抽成 static，`coverage.process` 从 true 变成 false。这件回忆最终没有计入合格数量，虽然没有删掉递线、解线的事实。

草稿实际正确采用了外婆；搬家年份也实际改成了 1962 年。这两项更正落入文本的能力是有效的，但不代表事件判定稳定。纳鞋垫草稿末尾还保留了兜底回答“一点我已经记不清了”，阅读时缺少明确指代。

模块 AI 在保存第 5 件后把已明确更正的人物、年份报为矛盾，第 6 件后又报无矛盾。`chapter_ready` 最终为 true，但这个转换不能用来证明模块收敛判断可靠。

建议：状态变化也能构成事件推进，不能只认两个 actual 直接相连。更正人物或年份应更新对应事实，保留其余经过；明确已解决的更正不能再次当作未解决矛盾。

## 做得顺的部分

M01 六段完整口述均保留全过程，没有要求补具体年份、感受或编造原因。每件均经过补充邀请、核对草稿、实际保存，之后才进入下一道主问题。

M04 的连续补充能够进入同一件草稿，没有自动新建故事；两次明确更正在生成文本中采用新人物和新年份。M03 已明确“不想讲后面的事情”时，没有再强迫追问后续。M03 踢毽子明确年份未知，已有经过没有因此被要求再补年份。

这些结果说明现有接口、保存推进和部分承接规则有用；主要问题在语义抽取、问题选择与完整性计算的衔接，不是简单换一个模型就能解决。

## 时间与下一步

46 次成功、需要模型处理的用户消息，服务端内网 HTTP 耗时为 1.208–6.686 秒，中位数 2.914 秒；45 次在 6 秒以内，1 次年份更正为 6.686 秒。22 次草稿生成最长 1.387 秒。控制器直接响应的“没有补充了”未混入这些模型消息耗时，失败请求也另计。

测量包含 API 和后端处理，但从服务器内部发出，不包含手机到云端的网络和 UI 渲染，不能作为客户端时延承诺，也没有足够长回复样本验证 10 秒指标。

建议下一轮依次处理：**先让跳过可靠推进，再修短答的选事件和人物指代，随后修事件缺口追问与语义覆盖，最后修更正后的状态稳定性。** 修后优先重跑这四组，比较原失败片段，再补真实老人说法的人工体验；不要用大段完整回答的成功替代短答验收。
