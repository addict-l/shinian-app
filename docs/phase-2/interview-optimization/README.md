## 接入后端（v3j + v4d）

### 切换与回退

| 环境变量 | 取值 |
| --- | --- |
| `INTERVIEW_PIPELINE` | `v2`（代码默认、旧流程）或 `v3j_v4d`（本轮云端启用） |
| `INTERVIEW_V3J_RUNTIME_DIR` | 新运行合同目录，镜像内为 `/app/app/ai/interview_runtime_v3j_v4d` |
| `INTERVIEW_V3J_RUNTIME_MANIFEST_SHA256` | 该目录 `manifest.json` 的 SHA-256，当前 `8897f3c50690d70571e8b8bf2acf2176c80caf17c860ddf6f207c2470a3ba99f` |

现有 `INTERVIEW_RUNTIME_DIR` / `INTERVIEW_RUNTIME_MANIFEST_SHA256` 照旧保留（题目目录、人生骨架的题目与 v2 流程仍用它）。同一个开关同时作用于访谈入口和人生骨架。设为 `v3j_v4d` 时 API 启动即校验新目录：manifest pin、每个文件哈希、目录里没有未列出的文件、三处模型参数只有评测时的五项且 thinking disabled（模型名 `deepseek-v4-pro` 由 manifest 哈希固定）、题号题序与入口问题和现网运行合同完全相同；任一不符则 API 起不来（与现有 pin 相同）。
**回退**：把 `INTERVIEW_PIPELINE` 改回 `v2`（或删掉这一行）并重建 API 容器；没开始的题立即回到 v2。已经在新流程里开始的那一题会按标记用新流程答完，所以回退后先保留两个 `INTERVIEW_V3J_*` 变量，等这些题结束再删。部署步骤见[后端部署说明](../../../cloud-deployment/backend/DEPLOY_ALIYUN.md#采访新流程开关v3j--v4d)。

### 怎样标记新旧会话

按**题**标记：一题第一次进入流程时，把流程名（`pipeline: v3j_v4d`）和运行合同 manifest SHA 写进这一题自己的状态（访谈入口是这一题的 `contract_state`，人生骨架是 `life_interview.questions.<SK 题号>`）；没有这个标记的题都是 v2 写的。骨架题本来就有状态项，所以“已开始”另看：已有原话、审计、判定结果或状态不是 `pending`（含 v2 下直接跳过的题）的骨架题都算 v2 已开始。已开始的题始终用它开始时的流程，没开始的题用当时的 `INTERVIEW_PIPELINE`。理由：

- 一题的原话、实际问句、待处理调用、已核验字段和审计都在这一题的 `contract_state` 里，题与题互相独立（运行合同 `question_context_mode=independent`），所以在题与题之间换流程不会把旧流程的待处理调用交给新流程，也不会用新流程重读旧答案；每次调用还绑定含 manifest、阶段、参数、提示和输入的 `request_sha256`，不同流程的记录本来也对不上。
- 后端的一个 chat session 只是一段故事（通常就是一题），而人物的整条采访状态会经 `following()` 一直往下传；按整条采访标记会让现有用户永远进不了新流程，回退也到不了已开始的人。按题标记时开关和回退都在下一题生效，与现有 v2 schema 迁移“在题与题之间切换、不重解释旧题”的做法一致。
- 新流程只用于现网 83 题目录（`runtime_version=full-interview-v2.0.0`）；旧 62 题目录的采访、旧 6 题骨架继续用旧运行合同。
- 判定结果仍是同一个引擎的结果结构，题内只多了 `followups`、`asked_target` 两项；人物级只多一个 `speaker_last_close`（上次收尾时说话层说的话）；人生骨架的 `life_interview` 同样只在骨架题里多 `followups`、`asked_target`、`asked_question`（上次实际问出的问句），整体多一个 `speaker_last_close`。旧镜像读到这些会忽略它们，但会用 v2 重判进行中的新流程题，所以回退请改变量而不是只换旧镜像。

### 调用与持久化

- 判定（judge）、否认复核（verify）、说话层（speaker）三类调用都经 `save_call` 先写进这一题的 `pending.calls`（骨架是这次请求的 `life_interview.pending.calls`）再进行下一步；重试同一请求时按 `request_sha256` 原样复用，不再调用。说话层调用失败不报错，记为失败并用固定句回退，重试也不再调用。显式“跳过”时的说话层调用另存在题内 `skip` 记录，不覆盖仍待重试的旧回答。
- 判定层与 `tools/interview_eval/pipelines/v3j.py` 逐行对应（同样的 system/user 消息、参数、拼装、verify 触发条件和引擎调用）；Node 桥是新的 `contract_interview_v3j_bridge.js`（常驻一轮判定，操作同评测桥），旧运行合同和旧桥不变。差别只在失败处理：调用失败沿用后端语义（保留原话、显式重试续跑），判定 invalid 时同 v2 一样保留失败、不向老人发问。

### 说话层在访谈入口的做法（与模拟器的差异）

说话层的提示、配置、输入构造、解析、清洗与收尾规则来自 v4d（`speaker-config.json` 的追问上限 2、同一目标 1 次、老人说“不想讲/记不清/累了”即收）。“对话”取自本 session 的消息：入口问题，加上每段回答和它之前老人看到的那条完整消息；判定层记的“原问”与模拟器一样只取问句部分（追问不含承接、转题只取下一题入口、草稿步骤只取固定句）。“已记下”取本题最后一次判定。按用户 2026-10-22 的决定：

| 情形 | 模拟器（v4d） | 后端 |
| --- | --- | --- |
| 追问（引擎 ask / ask_defer） | 说话层写承接 + 问句 | 相同；问句校验不过退回引擎问句（合格的承接保留），调用失败时就是引擎问句 |
| 一题聊完（ready、信息有限，以及老人说记不清、追问到上限） | 收尾一句后直接问下一题 | **保留草稿步骤**：说话层输入与模拟器相同，只取它的承接（去掉“换个话题”“再聊聊”这类转题分句），后接原句“这段可以先整理成草稿了。您还有什么想补充的吗？”并带 `offer_generation`；承接为空、含保存/整理/草稿等词或调用失败时只发原句；之后的补充、核对、保存不变 |
| 明确不想答（“跳过”等控制、引擎 skipped / deferred / limited+declined，以及老人说“不想讲”） | 体谅一句再问下一题 | 相同；失败或校验不过退回 `SKIP_ACK` + 下一题；不出保存入口；模块最后一题时下一项仍是模块菜单 |
| 老人说累了 / 引擎 paused | 先歇，点“继续”后进下一题 | 保持现有暂停：固定句，位置保留 |
| “上次换话题时你说的” | 上一题收尾整句 | 草稿步骤只记它显示过的承接，转题记整句 |
| 下一题 | 会话计划里的 4 道连续题 | 模块内下一题或模块菜单 |

### 人生骨架（SK 题）的做法

骨架 11 题走人生概览接口（`contract_life_overview.perform`），答案填进人物的人生概览，没有草稿步骤。开关为 `v3j_v4d` 时，没开始的骨架题由 `app/services/contract_v3j_life_overview.py` 处理：判定与访谈入口是同一个 `V3jPipeline`、同一个运行合同，说话层的输入构造、校验、收尾规则也相同；“对话”取自人生概览的 `turns`（入口问题，加上每段回答和它之前老人看到的那条完整消息），“原问”取这一题上次实际问出的问句（追问只取问句部分，否则是入口问题）。按用户 2026-10-22 的决定：

| 情形 | 模拟器（v4d） | 骨架（后端） |
| --- | --- | --- |
| 追问（引擎 ask / ask_defer） | 说话层写承接 + 问句 | 相同；问句校验不过退回引擎问句，调用失败时就是引擎问句；概览的“当前问题”是实际问出的问句 |
| 一题聊完（ready、信息有限，老人说记不清、追问到上限） | 收尾一句后直接问下一题 | **相同**（骨架本来没有草稿步骤）：`compose_close` 的“承接 + 下一道骨架题”；失败或校验不过退回原来的“我记下了。”+ 下一题 |
| 明确不想答（“跳过”等控制、引擎 skipped / deferred / limited+declined，老人说“不想讲”） | 体谅一句再问下一题 | 相同；失败退回 `SKIP_ACK` + 换行 + 下一题；显式“跳过”不调判定 |
| 最后一道骨架题之后 | 收尾一句（“今天先聊到这儿”） | 不调说话层，仍是原核对句“这些是您提供的人生线索……”，之后的核对、更正、确认不变 |
| 老人说累了 / 引擎 paused / “暂停” | 先歇，点“继续”后进下一题 | 保持骨架现有暂停：固定句，`paused`，这一题不结束，“继续”后接着问它的入口问题 |
| 下一题 | 会话计划里的 4 道连续题 | 下一道未完成的骨架题（`active_id` 的同一规则） |
| “上次换话题时你说的” | 上一题收尾整句 | 上一道骨架题收尾整句（含失败时的固定句），存在 `life_interview.speaker_last_close` |

收尾规则替引擎结束追问时（引擎仍是 ask，但老人说不想讲 / 记不清，或追问到上限），概览状态这样定（本次自定，与 v2 对引擎结果的映射一致）：不想讲为 `declined`，记不清为 `unknown`，追问到上限时有已答要素为 `known`、否则 `unknown`；引擎自己的 ready / limited / skipped / deferred 与 v2 完全相同。概览字段仍由判定结果的 `fields[].evidence` 投影（判定结果结构同引擎），`LifeField`、确认后的背景引文和 App 读到的结构都不变。

默认 v2 时骨架走原代码，`life_interview` 的内容与改动前逐字节相同（见下文验证）。

  - 骨架题：14 次判定结果、14 次收尾规则动作、10 次说话层输入与模拟器逐字相同；2 次追问、8 次“聊完接下一道骨架题”的最终文字也逐字相同（这正是 v4d 模拟访谈测过的收尾 + 下一题形式）。骨架的“下一题”“上次换话题”用后端自己的值，没有替换：夹具把计划外的骨架题记为此前已答，使后端自己的下一题就是模拟计划的下一题。差异 5 处，均为设计内：计划内最后一题（侯鎮清 SK03d、曹玉昌 SK03d）后端没有下一道骨架题，保持原核对句、不调说话层；2 次累了保持原暂停句（陈美龄 SK04、曹玉昌 SK03）；曹玉昌 SK03 暂停后后端这一题不结束，模拟器直接进下一题（回放把它记为已结束以接着回放）。完整骨架里真实值会不同的 5 处也列在输出里：SK03d 之后还有 SK04（2 处，“下一题”会是它），以及每段第一题之前还有骨架题（3 处，“上次换话题”可能是那道题的收尾）；这些输入没有缓存，需真实调用验证。
