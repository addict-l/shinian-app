2. 检查正在运行的 API、数据库、旧迁移及磁盘，确认可以备份并部署。
3. 备份源代码、生产配置、MySQL 和照片，保留原镜像标签 `shinian-api:rollback-3a1121c`。备份位于服务器 `/opt/shinian-validation/backups/pre-3a1121c-20261010/`，仅根用户可访问，不下载家庭业务数据到工程。
4. 从已提交的后端源码打包，在独立目录构建候选镜像 `shinian-api:candidate-3a1121c`。实际生产配置不放入代码包或镜像。
5. 在候选镜像中创建随机云端测试库，运行迁移与 30 项测试，结束时删除该测试库。模型调用使用替身，正式家庭数据库不承担测试清理。
6. 同步正式源代码，保留 `.env.production` 与 Docker 数据卷；旧测试源码移至独立验证目录。将已测试候选镜像标记为 `backend-api:latest`，只重建 API 服务。
7. API 启动执行 Alembic，正式数据库从 `c82b74920002` 升级至 `d10100000001`。
8. 检查正式健康接口、现有会话消息、新字段、表行数、镜像版本及公网 HTTPS。通过后才提交本次部署记录和新的提交顺序规则。

## 回退注意事项

旧镜像不认识新迁移 `d10100000001`，因此不能直接替换为旧镜像后启动。回退前先停止 API 写入并对当前数据库和媒体重新备份。

若数据库已经完整升级、需要立即回退，先使用含新迁移的候选镜像、现有 Compose 环境及数据库网络执行 `alembic downgrade c82b74920002`，确认降级成功；再恢复备份源代码，将保留的旧镜像重新标记为 `backend-api:latest`，重建 API，检查旧迁移、健康接口及现有数据。生产配置和数据卷保留。

降级会删除此次新增字段，无法保留升级后写入这些字段的新内容。若已有新数据，应先制定数据保留方案；若迁移中途失败，也不能假设 MySQL DDL 会自动回滚，应根据备份与实际表结构制定恢复步骤。本次部署正常，未在正式数据库执行回退。
