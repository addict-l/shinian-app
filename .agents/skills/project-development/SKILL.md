# 拾年项目开发流程

按下面的阶段推进，每个业务提交块都完成一次验证与人工审核。
沿用会话中已经确认的决定和授权，只询问未决事项；用户后续明确修改流程时，以最新指示为准。

## 1. 确认业务边界

调用当前可用的 grilling skill 执行问答（用户称其为 grill-me；按实际 skill 名称加载）。
每轮提出当前能够决定的问题，并给出推荐答案；能从仓库、文档或工具查到的事实由代理调查。
明确用户场景、本次包含与排除的功能、异常情况和可检查的验收标准。
将结论汇总给用户，获得明确确认后进入提交拆分与实现；已经确认的结论直接复用。

## 2. 拆分业务提交

把本次业务拆成有先后顺序的提交块；每块说明目标、范围、验收方法和拟用的 commit 标题。
每个提交应对应可独立解释和验证的业务变化，不机械地按文件数量拆分。
向用户展示提交计划；执行中发现新的业务边界时，更新计划并确认发生变化的边界。
正式 commit 在该块人工审核通过后创建。

读取 [项目环境说明](references/project-environment.md)，结合实际仓库配置核实构建、阿里云测试环境、Git 远程和主分支。
环境文档与实际配置冲突时，以实际配置和用户最新确认作为依据，并修正文档中的过时信息。

## 3. UI 设计确认（涉及 UI 时）

调用当前可用且适合技术栈的 UI 设计 skill，默认采用 ui-ux-pro-max；其他设计或实现 skill 按任务需要加载。
新增页面或大幅改版：先给出页面结构、关键交互和视觉方案，用户明确确认后再实现。
小幅 UI 修改：沿用既有设计，在实现后的人工审核中确认。
iOS 的运行效果使用环境说明中指定的现有 iPhone 17 模拟器验证。

## 4. 每个提交块的开发循环

依次执行：写代码 → 本地检查 → 阿里云／模拟器验证 → 提供审核材料 → 用户明确通过 → 正式 commit → 推送 GitHub 主分支。

### 实现与本地检查

完成本块业务变化，执行适合改动范围的 Xcode 构建、静态检查及必要测试，记录结果。
验证失败后返回修改阶段，修复后重新执行受影响的检查。

### 阿里云与模拟器验证

- 涉及云端的改动，在已确认的阿里云测试或演示环境验证；涉及后端发布时遵循项目部署文档的备份、候选验证、健康检查和回退约束。
- 涉及 iOS 的改动，在指定的现有 iPhone 17 模拟器上构建、安装、运行并验证。
- 涉及客户端与服务端交互时，完成模拟器和阿里云环境的联调。
- 与本块无关的验证项注明不适用；有关验证受阻时，保留修改并说明缺失项，补齐后再进入人工审核。
- 健康检查、迁移成功或单元测试通过不能替代完整业务验收；按本块验收标准检查实际行为。

正式生产发布是独立动作，只有用户明确授权后才执行。

### 人工审核

提供本块的业务变化、验收结果、实际执行的验证及其结果；UI 改动附截图或操作演示，并给出可复核的操作方法。
完成材料后，请用户审核，等待其明确通过当前提交块。
需求确认、设计确认和沉默均不等于代码审核通过。
审核失败后修改并重新验证；审核通过后若代码发生变化，重新完成受影响的验证和审核。

### 正式提交与推送

用户明确通过本块后，检查 diff 并只提交该块已审核的修改，然后直接推送 GitHub 的实际主分支。
本项目远程为 `origin`，主分支为 `main`；仍以当前 Git 配置和远程默认分支核实为准。
推送前检查远程更新；正常推送受阻时调查原因并处理，保留已审核结果，避免强制覆盖远程历史。
若合并远程变化改变了本块行为，重新验证并请求对变化部分的审核。
报告 commit 标识、推送结果和本块完成情况，再进入下一块。

## 完成条件

本次验收标准全部满足，每个提交块都已完成相关验证、明确人工审核、正式 commit 和主分支推送。
汇总实现结果和验证证据；仍受阻的步骤明确标为未完成，并说明所需信息或动作。
